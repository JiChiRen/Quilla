# `tools/_keytest/` — default developer keypair (ships with the repo, publicly known)

> This directory holds the repository's **default sample keypair**. For the
> authoritative guidance see [`tools/README.md`](../README.md) and
> [`doc/secure-boot.md`](../../doc/secure-boot.md) §2.5. TL;DR — `private.hex` is
> intentionally public so a fresh clone works out of the box (dev + SEALED/SEC
> upgrade); **do not use the default key in production firmware** — generate your
> own keypair.

## 0. Works out of the box (a default keypair ships with the repo)

This repository **ships with a default Ed25519 keypair** (`private.hex` +
`public.hex`), and `public.hex` is **the same key** as the public key compiled
into QBOOT. Therefore:

- **Clone and go**: after `git clone`, no key setup is needed to run the full
  secure-boot chain `build → boot → sign` (verify + anti-rollback). Dev boards
  flashed straight from the factory already contain this default public key in
  QBOOT, and the host signs with the matching `private.hex`, which is accepted.
- The default build (`QUILLA_QBOOT_DEFAULT_KEY` enabled) **compiles the public
  key into QBOOT**; the host **loads the private key at signing time** via
  `--key private.hex` — that is the division of labor: the private key never
  enters firmware, it is only a tool argument on the signing station.

> ⚠️ **This is the repository default (public) key; anyone can obtain
> `private.hex` from the repo.** It is **intentionally distributed with the public
> repository** (fresh clone works out of the box: the default QBOOT compiles in
> the matching public key, and the host signs with `--key private.hex`). But it
> is **strictly forbidden to use this default key in production firmware** — any
> product shipped to end users must replace the public key with its own and sign
> with its own private key (see §3). As long as the default (public) key remains
> in QBOOT, anyone can sign an arbitrary image and the device will accept it —
> this is "looks like secure boot but isn't", which is more dangerous than not
> enabling it at all.

## 1. Directory contents

| File | Contents | Confidentiality |
|------|----------|-----------------|
| `public.hex`  | 32-byte default public key (hex), **identical** to the `QUILLA_QBOOT_DEFAULT_KEY` branch public key in `quilla-qboot-pubkey.h` | Public |
| `private.hex` | 32-byte default private-key seed (hex), used by the host for signing | **Public (default sample key, ships with the repo)** |

`public.hex` / `private.hex` are generated by
`tools/quilla_ed25519_sign.py keygen`. Both must be **the same key** as the
public key embedded in `quilla-qboot-pubkey.h`; otherwise signed images fail
verification (see the §2.1 self-check).

## 2. Everyday developer usage

### 2.1 Out of the box: sign directly (default key)

```bash
# at the quilla repository root
python tools/quilla_host_upgrader.py <COM> app.bin \
    --key tools/_keytest/private.hex
```

- **`--key` points at the private-key file** — this is where "the private key is
  loaded by the tool": the private key is **not** compiled into firmware; it is a
  host argument on the signing station and is never visible to the device at
  runtime.
- Without `--key`: the host sends no SIGN frame, and the device skips
  authenticity verification (SHA-256 integrity only).
- Self-check (confirm this directory's private key is the same key as the header
  public key):

  ```bash
  python tools/quilla_ed25519_sign.py pubkey --key tools/_keytest/private.hex
  # the output must match, byte for byte, the key embedded in quilla-qboot-pubkey.h
  ```

### 2.2 Boot verification mode (SECURE / SEALED)

Whether the device runs a full Ed25519 verify on **every** power-up is decided at
compile time by `QUILLA_SB_BOOT_MODE` (see `doc/secure-boot.md`):

- `QUILLA_SB_BOOT_MODE_SEALED` (**default**): verification runs once at install /
  first boot; afterwards each boot only does SHA-256 + a seal compare (~0.6 s).
  To exercise the full verify chain itself, erase the seal in the META record or
  use `SECURE` mode directly.
- `QUILLA_SB_BOOT_MODE_SECURE`: a full Ed25519 verify runs on every power-up
  (~20 s) — the strongest re-authentication, at that cost on every boot.

## 3. ⚠️ Production: regenerate your own keypair

**The default key is for development / internal use only. Any firmware to be
shipped must switch to your own offline keypair.** Follow these three steps (the
complete "regenerate public and private key" flow):

### 3.1 Generate your own keypair (offline)

```bash
python tools/quilla_ed25519_sign.py keygen --dir <offline-secure-dir>
```

This outputs `private.hex` (secret) + `public.hex`, and prints a ready-to-paste
macro:

```
-DQUILLA_SECURE_BOOT_PUBKEY={0x..,0x..,...}
```

### 3.2 Get the public key compiled into QBOOT (replace the default key)

The standard secure-boot practice is to **compile the public key into firmware** —
the device uses it to verify at boot / install; the private key never enters
firmware. Wiring:

1. Add a product branch in `os/services/quilla-qboot/quilla-qboot-pubkey.h` with
   the `-DQUILLA_SECURE_BOOT_PUBKEY={...}` bytes printed in §3.1:

   ```c
   #if defined(QUILLA_QBOOT_PRODUCT_MYPART) && !defined(QUILLA_SECURE_BOOT_PUBKEY)
   #define QUILLA_SECURE_BOOT_PUBKEY { 0x..,0x.., ... }
   #endif
   ```

2. Enable that macro in the build (**remove** `QUILLA_QBOOT_DEFAULT_KEY`):
   - GNU: add `-DQUILLA_QBOOT_PRODUCT_MYPART` to the `C_DEFS` of
     `user/py32f040xb/EIDE/Makefile.qboot` (~line 134);
   - Keil: add `QUILLA_QBOOT_PRODUCT_MYPART` to the Define box of
     `user/py32f040xb/MDK-ARM/QBOOT.uvprojx` (a single token; a comma-containing
     list gets split apart in the Keil Define field, hence the "product macro"
     indirection).

3. A release build may add `-DQUILLA_PRODUCTION_BUILD`: if the repository default
   (public) public key is still compiled in, the header emits a compile warning
   reminding you to replace it (no longer a hard `#error`) — but shipping the
   default key is equivalent to handing over the private key, letting anyone sign
   for your device, so it must still be actively replaced.

### 3.3 Have the private key loaded by the tool (production key, **offline**)

- Keep the private key only in the §3.1 offline secure directory — **not in the
  repo, not in CI, not in the image**.
- Reference it at signing time via `--key <offline-secure-dir>/private.hex`,
  exactly as in §2.1, just with the path swapped for the production key — **the
  private key is always loaded by the signing tool, never compiled into
  firmware**.

## 4. Red lines

- `tools/_keytest/private.hex` is the repository default sample private key,
  **intentionally distributed with the public repository** (for out-of-the-box
  upgrades); it must **not** be used as a production signing key — a product must
  switch to its own keypair per §3.
- Any build aimed at end users: must switch to production keys per §3 (public key
  compiled into QBOOT, private key offline for the tool), and turn on
  `QUILLA_PRODUCTION_BUILD` (only makes the warning more prominent); the default
  key branch must be fully removed.
- If secure boot is not needed right now, the correct move is to **not flash a
  key** (bypass returns `QUILLA_SB_INACTIVE`) and state "secure boot not
  provided" in the argumentation document — better than keeping a useless key.

### 4.1 Path B: disable secure boot entirely (explicitly not enabled)

Applies when the product is confirmed to **not need** secure boot (a purely
internal tool, a closed environment, or a security argument that explicitly does
not cover firmware integrity). The approach is to return the device to
"pre-secure-boot" behavior — accept any valid image, run no Ed25519 verify, write
no seal.

**Mechanism**: when the key region is not Provisioned (all-0xFF fallback
default), `quilla_qboot_secure_pubkey_active()` returns 0 → `verify_app()` returns
`QUILLA_SB_INACTIVE` and the boot gate lets it through. So "disabling" simply
means **injecting no public key into the build**.

**Concrete steps (both toolchains must be handled — their factory defaults differ)**:

- **Keil (QBOOT target)**: open `user/py32f040xb/MDK-ARM/QBOOT.uvprojx`, and in
  the QBOOT target's **Define** box (currently
  `USE_HAL_DRIVER,PY32F040xB,QBOOT_BUILD,QUILLA_QBOOT_DEFAULT_KEY,QUILLA_SB_BOOT_MODE=QUILLA_SB_BOOT_MODE_SEALED`)
  **remove the `QUILLA_QBOOT_DEFAULT_KEY` entry**, keeping the rest. Do not add
  any `QUILLA_QBOOT_PRODUCT_*` macro, and do **not** pass
  `-DQUILLA_SECURE_BOOT_PUBKEY`.
- **GNU (Makefile.qboot)**: the `C_DEFS` of
  `user/py32f040xb/EIDE/Makefile.qboot` (~line 134) defaults to
  `-DUSE_HAL_DRIVER -DPY32F040xB -DQBOOT_BUILD`, which **already excludes
  DEFAULT_KEY and passes no `QUILLA_SECURE_BOOT_PUBKEY`**, i.e. it is INACTIVE by
  default. Just confirm no `-DQUILLA_QBOOT_PRODUCT_*` or
  `-DQUILLA_SECURE_BOOT_PUBKEY` has been added; usually no change is needed.

> ⚠️ **The two toolchains ship with different defaults**: Keil carries DEFAULT_KEY,
> GNU does not. When shipping from only one of them, be sure that **that** build
> has DEFAULT_KEY removed, or you get "thought it was off, actually still on".

**Verification**: after flashing, on boot the serial console should show
`sb-out=00000001` (`QUILLA_SB_INACTIVE`); the device boots normally, does **not**
run the 20 s verify, and writes no seal. If you still see `sb-out=00000000` (OK)
/ `00000003` (SEALED) or `REFUSED - signature invalid`, a key is still present —
> go back and check whether a Define entry was missed.

**Notes**:

1. **Delete the "macro", not the "bytes".** The correct move is to remove the
   `QUILLA_QBOOT_DEFAULT_KEY` **macro itself**; do not merely change the public-key
   bytes in `quilla-qboot-pubkey.h` — as long as that macro remains, the header
   re-compiles the default public key and DEFAULT_KEY still takes effect.
2. **Confirm both toolchains** (see the ⚠️ above). Missing either leaves DEFAULT_KEY
   residue behind.
3. **INACTIVE is not failure.** The device accepts any valid image; this is
   "explicitly not enabled", and the argumentation document must state "secure
   boot not provided". A keyless INACTIVE build does not conflict with
   `QUILLA_PRODUCTION_BUILD` — the latter only makes the warning more prominent
   when the default (public) key is compiled in, and does nothing when keyless.
   But if the goal is to enable secure boot, you must go through §3 to switch to
   your own key, not keep an empty key.
4. **SECURE / SEALED are meaningless under INACTIVE.** Any value of
   `QUILLA_SB_BOOT_MODE` has no effect — INACTIVE lets it through directly and
   the verify branch is never entered.
5. **Path B cannot be chosen when the goal is real secure boot.** If the goal is
   "enable secure boot", you must go through §3 (switch to production keys). Path
   B is "explicitly declare not provided"; both are better than "shipping with the
   default (public) key" — the latter is a false security claim (anyone with the
   repo can sign), but only Path A is real secure boot.
